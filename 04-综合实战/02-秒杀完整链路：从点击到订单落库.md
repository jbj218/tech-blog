# 秒杀完整链路：从点击到订单落库的每一步

> 这篇博客把 Redis、MyBatis-Plus、Spring Boot 全部串到秒杀一条线上，详细推演"用户点抢券"之后每个环节发生了什么。

## 一句话定位

**秒杀 = Lua 守门 + Stream 异步 + RedisIdWorker 拼 ID + Hutool 转 Bean + MyBatis-Plus 写库。** 这是一条完整的高并发抢券流水线，每一个组件各司其职。

---

## 一、秒杀的整体时序

```
T0 用户点击"立即抢购"
T1 Spring MVC 路由到 VoucherOrderController.seckillVoucher
T2 调用 VoucherOrderServiceImpl.seckillVoucher
T3 执行 Lua 脚本（Redis 原子判断）
T4 Lua 返回 0（成功）→ 生成订单 ID → XADD 发到 Stream
T5 Controller 返回 Result.ok(orderId) 给前端
T6 前端显示"抢券成功"

------ 异步链路 ------

T7 后台消费者 XREADGROUP 阻塞读到消息
T8 BeanUtil.fillBeanWithMap 把 Map 转 VoucherOrder
T9 voucherOrderMapper.insert(order) 写 MySQL
T10 XACK 确认消息已处理
```

## 二、同步链路：秒级判断（Lua）

### 2.1 为什么必须 Lua

```java
// ❌ 普通写法：两步不是原子的，必超卖
Long stock = stringRedisTemplate.opsForValue().get("seckill:stock:" + voucherId);
if (stock > 0) {
    stringRedisTemplate.decrement("seckill:stock:" + voucherId);   // 中间窗口被插足
}
```

**根因**：Redis 命令在多个客户端之间是交叉执行的（单线程轮询处理命令），查和改之间会被其他线程插入。

**Lua 解法**：Redis 单线程 + Lua 脚本 = "判断+扣库存+记录用户" 一气呵成。

### 2.2 Lua 脚本设计

```lua
-- KEYS[1] = 库存 key
-- KEYS[2] = 已抢用户 set key
-- ARGV[1] = 用户 ID

-- 1. 一人单判断
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then
    return 2   -- 已抢过
end

-- 2. 库存判断
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then
    return 1   -- 库存不足
end

-- 3. 扣库存 + 记录用户
redis.call('decr', KEYS[1])
redis.call('sadd', KEYS[2], ARGV[1])
return 0       -- 抢券成功
```

### 2.3 Java 调用

```java
Long result = stringRedisTemplate.execute(
    new DefaultRedisScript<>(SECKILL_SCRIPT, Long.class),
    List.of("seckill:stock:" + voucherId, "seckill:order:" + voucherId),
    userId.toString()
);

if (result != 0) {
    // 1: 库存不足, 2: 已抢过
    return Result.fail(result == 1 ? "库存不足" : "您已抢过");
}
```

## 三、同步链路：拼订单 ID

```java
long orderId = redisIdWorker.nextId("order");
```

`RedisIdWorker` 的工作原理：

```java
public long nextId(String keyPrefix) {
    long timestamp = LocalDateTime.now().toEpochSecond(ZoneOffset.UTC) - BEGIN_TIMESTAMP;
    String date = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);
    return timestamp << 32 | count;
}
```

**为什么这么设计**：

| 设计 | 作用 |
| ---- | ---- |
| 按天切分 key | 单 key 不会无限增长 |
| `timestamp << 32 | count` | 一个 Long 表达两个信息，趋势递增 |
| Redis INCR | 天然原子、不需要额外加锁 |

## 四、同步链路：发订单到 Stream

```java
Map<String, Object> message = Map.of(
    "userId", userId.toString(),
    "voucherId", voucherId.toString(),
    "id", String.valueOf(orderId)
);
stringRedisTemplate.opsForStream().add("stream.orders", message);
```

**为什么用 Stream 而不是直接写 DB**：

- 用户点抢券要求响应快（毫秒级）
- 写 DB 慢（几十 ms），且数据库连接有限
- Stream 起到"削峰"作用：把所有抢券请求的消息缓存起来，消费者按 DB 承受的速度慢慢处理

## 五、异步链路：消费者

### 5.1 启动

```java
@Component
public class VoucherOrderConsumer implements ApplicationRunner {

    @Override
    public void run(ApplicationArguments args) {
        // 应用启动后，开启独立线程消费
        handlerThread.start();
    }
}
```

### 5.2 循环读取

```java
while (running) {
    List<MapRecord<String, Object, Object>> records = stringRedisTemplate
        .opsForStream()
        .read(Consumer.from("g1", "consumer1"),
              StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
              StreamOffset.create("stream.orders", ReadOffset.lastConsumed()));

    if (records == null || records.isEmpty()) continue;
    handleRecords(records);
}
```

### 5.3 处理单条消息

```java
private void handleRecords(List<MapRecord<String, Object, Object>> records) {
    for (MapRecord<String, Object, Object> record : records) {
        try {
            // 1. Map → Bean
            VoucherOrder order = BeanUtil.fillBeanWithMap(
                record.getValue(), new VoucherOrder(), true);

            // 2. 写 DB
            voucherOrderMapper.insert(order);

            // 3. ACK
            stringRedisTemplate.opsForStream().acknowledge(
                "stream.orders", "g1", record.getId());
        } catch (Exception e) {
            // 4. 失败处理（一般重试或进死信队列）
            log.error("处理订单失败", e);
        }
    }
}
```

**关键点**：

- `BeanUtil.fillBeanWithMap(map, new VoucherOrder(), true)` —— 第三个参数 true 表示**忽略大小写、自动转换类型**
- ACK 之后消息才从 Pending List 移除，**保证至少一次消费**

## 六、Redis 数据结构选型对照

秒杀涉及 4 个核心数据结构，对应不同 Redis 类型：

| 数据 | 类型 | 用途 |
| ---- | ---- | ---- |
| `seckill:stock:{voucherId}` | **String** | 库存计数 |
| `seckill:order:{voucherId}` | **Set** | 记录已抢用户 |
| `icr:order:{yyyy:MM:dd}` | **String** | RedisIdWorker 序列号 |
| `stream.orders` | **Stream** | 订单消息队列 |

**为什么不用其他类型**：

| 类型 | 适合 | 不适合的原因 |
| ---- | ---- | ---- |
| List | 队列 | 不能 ACK，断电丢消息 |
| Hash | 对象 | INCR 不方便 |
| Set | 去重集合 | 不能排序（排行榜才用 ZSet） |
| ZSet | 排序去重 | 抢券不需要排序 |

## 七、一致性与补偿

### 7.1 同步链路丢消息怎么办？

如果 Lua 成功了、XADD 之前服务挂了 → 用户看到的"抢券成功"实际没有订单记录。

**应对**：补偿机制——定时任务扫描 `seckill:order:{voucherId}` Set，找出已抢用户但 stream 队列里没有对应消息的，重新生成订单。

### 7.2 异步链路丢消息怎么办？

Stream + ACK 机制保证至少一次消费。如果消费者崩溃，消息留在 Pending List，下次启动重新消费。

### 7.3 Stream 消息堆积怎么办？

Stream 是 Redis 内置的持久化结构（默认不会因为消费完就删除），堆积只是占内存。需要清理时 `XDEL` 或 `XTRIM`。

## 八、一句话总结

| 链路阶段 | 动作 | 技术 |
| ---- | ---- | ---- |
| **同步-1** | 判断资格 + 扣库存 | Lua 脚本（Redis 单线程原子） |
| **同步-2** | 生成订单 ID | RedisIdWorker（INCR + 位运算） |
| **同步-3** | 异步发消息 | Redis Stream XADD |
| **同步-4** | 立刻返回 | Spring MVC Result.ok |
| **异步-1** | 阻塞读消息 | XREADGROUP |
| **异步-2** | Map → Bean | Hutool BeanUtil |
| **异步-3** | 写 DB | MyBatis-Plus insert |
| **异步-4** | 确认消费 | XACK |

**整条链路的精髓**：**同步做轻活、异步做重活**——Lua 判断立刻返回，DB 写入后台慢慢跑。Redis 单线程模型撑住了判断的原子性，Stream 撑住了消息不丢，MyBatis-Plus 撑住了 DB 写入的简洁。
