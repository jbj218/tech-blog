# 商户查询缓存：缓存三大问题与互斥锁方案

> 这篇博客对应我学过的《Redis实战篇》商户查询缓存 + 互斥锁部分。

## 一句话定位

**缓存击穿 / 穿透 / 雪崩是缓存系统最经典的三大问题。** 它们各自针对不同场景，解决方案也完全不同——但底层逻辑都围绕"如何让缓存持续可用"。

---

## 一、为什么要加缓存

```
用户请求 → 缓存（有就返回）→ MySQL（没才查）→ 写回缓存
```

**收益**：挡掉 99% 的 MySQL 请求，把单台 MySQL 撑住的并发从 4000 提升到几十万。

**代价**：引入了**缓存与数据库数据不一致**的问题——所以缓存通常存"读多写少、对一致性要求不那么高"的业务（店铺信息、商品详情……）。

---

## 二、缓存三大问题全景

### 2.1 缓存击穿

**场景**：某个**热点 key** 突然过期（或首次加载），恰好这一瞬间有海量请求同时打过来。

**后果**：海量请求全部穿透到 MySQL，把数据库打挂。

**关键特征**：单个热点 key、高并发、缓存失效瞬间。

### 2.2 缓存穿透

**场景**：查询一个**根本不存在的数据**（比如 ID=-1 的用户），缓存里没有，数据库里也没有。

**后果**：每次请求都要打到数据库，且永远查不到 → 缓存形同虚设，恶意攻击专门用这个漏洞。

**关键特征**：数据根本不存在、缓存和 DB 都查不到、攻击常用。

### 2.3 缓存雪崩

**场景**：**大量 key 同时过期**（比如零点统一过期），或 Redis 整个挂了。

**后果**：请求洪流涌向 MySQL，数据库崩溃。

**关键特征**：大面积失效 + 高并发叠加。

---

## 三、解决方案对照表

| 问题 | 核心思路 | 具体方案 |
| ---- | ---- | ---- |
| **击穿** | 让重建缓存只发生一次 | 互斥锁 / 逻辑过期（永不过期 + 后台异步重建） |
| **穿透** | 让"不存在"也能被缓存 | 缓存空值 / 布隆过滤器 |
| **雪崩** | 让 key 不要同时失效 | 过期时间加随机扰动 / 多级缓存 / Redis 高可用集群 |

## 四、互斥锁方案（击穿）

### 4.1 原理

**核心**：第一个抢到锁的线程去查 DB 重建缓存，其他线程原地等 + 重试。

```java
// 获取锁：SETNX + EX 一句话搞定
private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", 10, TimeUnit.SECONDS);   // SETNX + EX 原子操作
    return BooleanUtil.isTrue(flag);
}

// 释放锁
private void unlock(String key) {
    stringRedisTemplate.delete(key);
}
```

### 4.2 为什么不直接 `return flag`

```java
// ❌ 错误写法
Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
return flag;   // flag 可能是 null！

// ✅ 正确写法
return BooleanUtil.isTrue(flag);
```

`setIfAbsent` 的返回值是 `Boolean`（包装类，不是基本类型）。Redis 网络超时、连接断开、方法抛异常时**可能返回 null**：

- 上层用 `if (flag)` 自动拆箱 → NullPointerException
- 上层把 null 当 false 处理 → 业务逻辑错误

`BooleanUtil.isTrue(flag)` 源码：

```java
public static boolean isTrue(Boolean bool) {
    return bool != null && bool;   // null → false
}
```

### 4.3 为什么必须设过期时间

> **不设时间会死锁**——线程执行 `delete` 释放锁前崩溃了，Redis 里的 key 永远不被删 → 后续所有 `setIfAbsent` 都失败 → 整个系统死锁。

设了过期时间又引出新问题：

```
线程 A 拿到锁，设置 10 秒过期
doBusiness() 耗时 15 秒（超过 10 秒）
→ 锁自动过期 → 线程 B 可以拿到锁
→ 线程 A 终于跑完，执行 redis.delete("lock") → 删的是线程 B 的锁！
→ 线程 B 的业务还在跑 → 数据错乱 ❌
```

这就是著名的**"锁误删"问题**。

### 4.4 解决锁误删：UUID + Lua

加锁时 value 设为唯一标识（UUID），释放锁前先比对标识再删除——**用 Lua 脚本保证"比对 + 删除"是原子的**：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

```java
String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
redis.execute(new DefaultRedisScript<>(script, Long.class),
              Collections.singletonList("lock"), uuid);
```

**生产级方案**：直接用 **Redisson** 框架（自动续期 + 看门狗机制），30 秒默认过期 + 每 10 秒检查续期。

## 五、为什么抢到锁后还要再查一次缓存（双重检查）

```
Thread A                          Thread B
① 查 Redis → null
② 抢锁 → 成功 ✓
③ 查数据库...（很慢）
                                  ① 查 Redis → null
                                  ② 抢锁 → 失败，休眠 50ms
                                  ② 抢锁 → 失败，休眠 50ms
④ 写入 Redis ✓
⑤ 释放锁 ✓
                                  ② 抢锁 → 成功 ✓
                                  ← 此时 Redis 里已经有数据了！
                                  → 不二次检查 → 白查一次数据库 ❌
                                  → 二次检查 → 直接返回缓存 ✅
```

**根因**：第一次查缓存和拿到锁之间有时间差，别的线程可能已经把缓存重建好了。

这就是经典的 **Double-Checked Locking（双重检查锁定）** 模式——第一次检查在锁外，第二次检查在锁内。

## 六、缓存穿透的两个解法

### 6.1 缓存空值

查 DB 没查到 → **在 Redis 里写一个空标记**（比如 `""` 或 `null`）→ 下次同样的请求直接被缓存拦掉。

```java
Shop shop = queryFromDB(id);
if (shop == null) {
    // 缓存空值，过期时间设短一点（比如 2 分钟）
    stringRedisTemplate.opsForValue().set("shop:empty:" + id, "", 2, TimeUnit.MINUTES);
    return null;
}
```

**优点**：简单粗暴；**缺点**：占内存，且如果有真实数据了要主动清掉这个空标记。

### 6.2 布隆过滤器

把"可能存在的 ID"用一个布隆过滤器先筛一道——过滤器说没有就一定没有（但说有不一定真存在，有小概率误判）。

**优点**：省内存（位图）；**缺点**：有误判率，且不能删除（标准布隆过滤器）。

## 七、缓存雪崩的两个解法

| 方案 | 做法 |
| ---- | ---- |
| **过期时间加随机扰动** | 给每个 key 的 TTL 加 ±10% 的随机偏移，避免同一时刻大量失效 |
| **Redis 高可用** | 主从 + 哨兵 + Cluster，挂了自动切换 |
| **多级缓存** | 本地缓存（Caffeine）+ Redis + DB，多层兜底 |
| **熔断降级** | 用 Sentinel / Hystrix 在 Redis 挂掉时直接返回兜底数据 |

---

## 八、一句话总结

| 问题 | 一句话方案 |
| ---- | ---- |
| **击穿** | 互斥锁（谁抢到谁查 DB）/ 逻辑过期（永不过期 + 后台异步重建） |
| **穿透** | 空值缓存 / 布隆过滤器 |
| **雪崩** | TTL 随机扰动 / Redis 高可用 / 多级缓存 |

**核心思想**：缓存三大问题本质上都是"缓存不可用导致流量打到 DB"——只要让缓存"在任何情况下都还能挡一部分流量"，问题就解了。
